# A1 renderer diagnostic recommendation

Read-only audit, 2026-10-29. This document records proposed diagnostics; this audit did not install packages, launch Kit, change the driver, or run a task/model. Package observations below describe the environment before the separately authorized stock installation. The coordinating agent has selected the complete stock baseline in item 2 below as the next A1 diagnostic; the smaller item 1 comparison is an alternative, not an automatic extra launch.

## Evidence and remaining uncertainty

Attempt A0-002 reached `KitApp.startup()` and crashed during `omni.usd.get_context().new_stage()`, before procedural scene construction or any RGB frame. The Python fault stack reaches `omni.kit.widget.viewport`'s Hydra-engine enable path. This establishes the failure boundary, not an exact native-library cause.

The launcher sets `CUDA_DEVICE_ORDER=PCI_BUS_ID` and masks CUDA to GPU UUID `GPU-e1a460e9-e272-b227-222e-0dbb77c248c5` (`scripts/provision_a0_launch.py:65`). Kit still enumerates eight physical GPUs and selects its index 4, PCI bus 81. Warp sees only `cuda:0`. The log explicitly warns about CUDA/Omniverse enumeration differences and possible crashes when `CUDA_VISIBLE_DEVICES` is set (`validation/provisioning/a0_attempt_002/stdout_stderr.log:24`), followed by repeated CUDA-bad-state warnings. Masking is therefore a concrete unresolved confounder, not a proven cause.

NVIDIA's [Linux troubleshooting, GPU selection](https://docs-prod.omniverse.nvidia.com/dev-guide/latest/linux-troubleshooting.html#q9-how-to-specify-what-gpus-to-run-omniverse-apps-on) says CUDA visibility does not select Vulkan devices; use Kit's GPU table and verify its active entry. Do not assume Kit and `nvidia-smi` indices always coincide.

There is also an [exact-version report for Isaac Sim 5.1 and driver 610.43.02](https://forums.developer.nvidia.com/t/isaacsim-crash-when-update-gpu-driver/371975). NVIDIA staff identify that driver as outside the validated production branch and recommend a supported production driver. The thread does not supply a successful software workaround or establish that every crash with this driver has the same cause. The [5.1 requirements](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/requirements.html) list Linux 580.65.06 as a tested driver. Host driver changes are outside this container's permitted operations.

## Exact installed API and packaging

`runtime/a0_env` currently contains `isaacsim`, `isaacsim-kernel`, and the three `isaacsim-extscache-*` 5.1.0.0 packages. Its `isaacsim/exts` directory is empty: `isaacsim.simulation_app` is not installed. The cache contains the vendor wheel at `/tmp/claude-0/-workspace/6db53f70-7510-4b1b-9d87-79dcd2a46bba/scratchpad/review_provisioning/wheels/isaacsim_core.whl`; metadata identifies 5.1.0.0. The extracted `simulation_app.py` in that directory was read without importing vendor code.

That exact source, lines 71–100 and 415–420, supports `headless`, `active_gpu`, `physics_gpu`, `multi_gpu`, `max_gpu_count`, `width`, `height`, and `renderer="RaytracedLighting"`. It does **not** expose the newer `active_cuda_gpus` option. Its configuration matches the [versioned 5.1 API](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/py/source/extensions/isaacsim.simulation_app/docs/index.html). `disable_viewport_updates` is applied after new-stage creation (lines 306–328), so it is not a reliable bypass for this initial crash.

The installed `apps/isaacsim.exp.base.python.kit` inherits `isaacsim.exp.base.kit`. Base requires multiple Isaac extension groups, including robot/sensor/GUI extensions. Merely installing `isaacsim-core`, or copying the launcher source, does not establish a complete stock experience. The core wheel also pins substantial dependencies, including torch 2.7.0. A stock-baseline preparation must resolve and record the complete pinned extension/package closure without silently upgrading Kit/Isaac Sim or downloading robot/task assets.

## Bounded next diagnostic

1. Lowest-change diagnostic: run the existing procedural camera script once in a fresh output/cache directory with `CUDA_VISIBLE_DEVICES` absent from the child environment. Retain `CUDA_DEVICE_ORDER=PCI_BUS_ID`; select GPU UUID/PCI bus explicitly through the verified Kit index, disable multi-GPU, and set the physics CUDA index only after checking unmasked CUDA ordering. This isolates the visible masking mismatch without an installation change. Do not change parent environment variables or global cache contents.
2. If that still fails, prepare a separately recorded complete stock 5.1 Python experience, then run one bounded procedural RGB sample through `from isaacsim import SimulationApp`. Candidate launch configuration: `headless=True`, `active_gpu=4`, `physics_gpu=4`, `multi_gpu=False`, `max_gpu_count=1`, `width=640`, `height=480`, `renderer="RaytracedLighting"`; both index values require current UUID/PCI verification. Pass the stock `isaacsim.exp.base.python.kit` explicitly and leave CUDA visibility unmasked. This configuration is a diagnostic candidate, not a proven fix.
3. Use the [5.1 standalone Replicator pattern](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/replicator_tutorials/tutorial_replicator_getting_started.html): construct SimulationApp before importing Omni modules, create only a procedural cube/light/camera, attach RGB to one render product, request a finite number of captures, detach, and close. Adapt its example to headless mode and a finite loop; do not copy its indefinite interactive loop or add semantic/bounding-box outputs.

Each launch needs its own manifest, environment allowlist, package inventory, full stdout/native crash logs, wall-clock deadline, process-group cleanup, and GPU-memory observation. Verify only the chosen GPU is active for rendering. Stop on crash, timeout, wrong active GPU, or an unexpected dependency/asset download. Review the evidence before choosing another configuration; no blind automatic retry.

A useful pass requires saved nonempty 640×480 RGB with visible procedural geometry, finite successful updates, and clean process termination. App startup alone is insufficient. Success would clear this render smoke test, not validate native RoboDojo, ARX control, observations, or MakeToast. Repeated failure with the stock unmasked baseline would materially strengthen the host-driver compatibility explanation; report that limit without attempting an in-container driver replacement. The full MakeToast attempt and Astra calls remain outside this diagnostic and require the previously agreed preview/approval flow.
