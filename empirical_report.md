Implication for lambda_ki: the groups partition the trainables disjointly (`_is_ki_clip`: ".lora_" or "ki_table." in oat/policy/p2n_vla_common.py:600-601; plus "siglip." in oat/policy/p2n_vla_vision_action.py:72-73); the AR loss cannot reach the ki group (expert reads detached VLM K/V, p2n_vla_common.py:433) and the KI loss cannot reach the ar group, so the KI loss is the only gradient of the ki group. Clipping (oat/workspace/train_p2n_vla.py:341) renormalizes that gradient to norm 1.0 at every step regardless of lambda_ki, and AdamW is scale-invariant per parameter besides. lambda_ki = 1.0 therefore acts only as an on/off switch (0 freezes LoRA/KI table, p2n_vla_common.py:202-205); any lambda_ki sweep would be a no-op. The monotonic growth of the pre-clip norms (gn_ar 2 -> 8.4, gn_ki 6 -> 20 in p2n_vla) while the loss falls indicates increasingly peaked predictions (memorization), and the logged norms are not the applied update magnitudes.

Explanation of the monotonic CE rise with rising SR: held-out argmax accuracy (0.087-0.101) and reconstruction MSE (0.048-0.055) are flat for 60k updates while CE rises 5.10 -> 7.33 and training accuracy goes 0.20 -> 0.94: the held-out predictive distributions become increasingly peaked on wrong codes (calibration collapse from memorizing 124k windows of 450 demos), not a loss of greedy-decode quality. The exact OAT code of a stochastic demonstrator is close to unpredictable from a single frame (every run/segment sits at 0.09-0.12 held-out token accuracy; chance is 1/5000), so held-out CE measures confidence on a high-entropy target rather than closed-loop competence; the simulator SR instead reflects greedy decoding in self-visited states, which the demo windows do not cover, and the trainable vision tower improves exactly the fine tasks (section 4). Consequence: teacher-forced held-out CE cannot be used for early stopping or model selection in either run (docs/P2N_VLA.md:480 already says never to select by CE). The generated-vs-expert history CE gap stays constant (+0.19-0.27 nats p2n_vla, +0.30-0.32 vision_action) across all of training: self-past at p=0.5 does not shrink the offline exposure-bias gap.

## 5. Reference points and protocol
- docs/P2N_VLA.md:514 names the 0.772-SR non-VLA self-past P2N policy (same OAT tokenizer) as the context baseline and docs/P2N_VLA.md:225 says it used the same 550-step budget. No official-protocol evaluation of that checkpoint exists on disk (output/eval holds only p2n_nano_ep0150_500_20261009_044910 and a nut_washer offline eval), and the 0.772 is the checkpoint filename's in-training SR from the legacy runner. Against it, p2n_vla is -33pp (0.446) and vision_action -7 to -10pp (0.678-0.706).
- output/training/p2n_new_original_obs_libero10 (non-VLA P2N, corrected protocol, 500 episodes, 550 steps): in-training SR 0.670 @ep100 falling to 0.398 @ep1100 - another in-repo non-VLA reference at ~0.67 peak, but corrected != official protocol.
- The official protocol here = LIBERO init states 0-49 per task via set_init_state plus 5 zero-action settling steps (oat/env/libero/env.py:195-202), seeds 3000-3499, 550 policy steps (oat/config/task/policy/libero/libero10_vla.yaml:79) versus LIBERO's 600 and openpi/OpenVLA's 520+10 (docs/P2N_VLA.md:225), so the numbers are not directly comparable with published pi0.5/OpenVLA LIBERO-10 results. autoreset is off for non-legacy protocols (oat/env_runner/libero_runner.py:246-252), so the legacy autoreset first-chunk swallow does not affect these evaluations. In-training evaluation reuses the final test schedule at every snapshot (docs/P2N_VLA.md:228 warns that picking the best snapshot is selection on test); best-vs-last differences are not significant in either run.

## 6. Anomalies
- skipped_optimizer_steps = 0 and train_nonfinite_losses = 0 in all 300 + 731 epoch records; all logged losses and grad norms finite; replica_fingerprint has 300/731 unique values, changes every epoch, no consecutive repeats, and the check (train_p2n_vla.py:1322-1334) never raised.
- logs.jsonl of p2n_vla has 30,011 train_step records for 30,000 steps: steps 20,001-20,011 are duplicated (lines 20205-20215 from the aborted 07:32 attempt, 20216-20226 from the final resume) with different values (mean loss_ar 2.13 vs 2.37, samples/s 10.4 vs 6.9 on the first step, memory 14.71 vs 16.02 GiB) and one non-monotonic step boundary; W&B only contains the final attempt. No checkpoint was written by the aborted attempt (checkpoint_every = 10 epochs), so weights were unaffected.
- Stale metric: val/expert/self_past_rows = 7.72-7.76 (p2n_vla) and 0.9725-0.9775 (vision_action) even though expert mode regenerates nothing; `_resolve_history` (oat/policy/p2n_vla_common.py:546) skips `_maybe_self_past` for history_mode='expert', so `_last_self_past_rows` (reset only inside `_maybe_self_past`, line 506) still holds the previous generated-mode count when it is logged (line 577). val/generated/loss_ki is bitwise equal to val/expert/loss_ki (expected; the KI pass is history-independent and is computed twice).
- Validation sets differ between runs (3,200 vs 400 windows; old vs new split) and across the p2n_vla resume, so no val number is comparable across runs or across the resume.
- The OAT tokenizer provenance check compares zarr_path/seed/val_ratio/max_train_episodes strings, not content (scripts/train_p2n_latent_flow.py:188-193): the frozen tokenizer (trained on the old zarr's positional split) passed preflight for vision_action on the rebuilt zarr, so ~45 of that run's 50 held-out demos were in the tokenizer's training set (minor action-only leak; affects val reconstruction MSE marginally, not SR).
- vision_action stopped by KeyboardInterrupt at step 73,100 (wandb output.log:750-876) with the cosine schedule 27% from its end; the 70k evaluation (0.678) exists on disk but is in no README (the HF README stops at 60k/62,100).
- Memory reserved changed 14.71 -> 16.02 GiB after the resume (different host) and back at 26k; p2n_vla rollouts on machine 2 took 39.5-40.0 min vs 36.5-37 min on machine 1.
- The pre-resume rollout summary.json files point their "snapshot" field at the machine-1 path (/workspace/past2next_bug_fixed/...).
- KI pathway in the LoRA run learns little: train KI token acc 0.24 and "val" 0.15 at 30k (vision_action: 0.975 train / 0.05 val); no lambda_ki=0 run exists to show whether KI helps SR at all.
